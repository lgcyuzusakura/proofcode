# ProofCode 项目、数据库、缓存与上下文实施方案

日期：2026-10-08。范围：项目与会话、桌面自动工程目录、数据库与 Redis 管理、版本感知 RAG、可回取上下文压缩、可执行对照实验。本方案不包含模型选型、免费额度、本地模型部署或推理硬件优化。本轮产物是设计文档，功能实现状态以代码审计表为准。

## 1. 最终要交付的日常开发体验

用户可以直接点击“新对话”，不需要先导入文件夹。桌面应用为这段新对话创建独立工程目录，保存项目身份，并让对话与实际执行工作区关联。用户也可以打开已有项目，在原目录下继续对话。

每个项目有自己的数据库连接、Redis 连接、对话、检索索引、操作计划、批准记录和恢复记录。切换项目后，界面和 Agent 都只能获得当前项目的资源。数据库表格编辑、拖拽查询与 Agent 生成的操作使用同一条受控执行链路。

例如：“给订单增加备注字段，并修改接口和测试。”系统先选定项目当前源码与数据库结构版本，查找实体、查询、接口和测试，准备代码补丁与数据库变更草稿，在临时环境验证，再展示用户需要批准的操作。数据写入始终经过批准；失败恢复根据 PostgreSQL 事务、提交后反向计划、Redis 条件补偿分别处理。

开发主体仍按此前确认的“核心后端优先”推进。“不导入目录也能开聊”需要桌面原生目录创建和最小入口接入，因此二者列入必做范围。数据库、缓存完整管理页面在后端闭环之后接入，页面契约和拖拽语义在本方案中一次确定。

## 3. 项目隔离与没有文件夹的对话

### 3.1 身份与隔离规则

应用层关系如下：

```text
Project（资源隔离单元）
├─ Workspace（工程目录、分支或工作树）
│  ├─ Conversation 1
│  │  └─ Task / Attempt / Transcript / ContextReference
│  └─ Conversation 2
├─ DataResource（PostgreSQL / Redis，带环境与版本）
├─ DataSession / OperationPlan / Approval / Audit / Recovery
└─ RevisionManifest / CodeIndex / SchemaIndex
```

一个新建的自动工程目录对应一个新的 Project 和 Workspace，避免把所有无需导入的对话放进全局 Scratch 项目。在已有项目里点击“新对话”则复用该项目与目录，新增 Conversation。同一项目的分支工作树可共享项目连接，但可再限制 workspace/environment 的可见资源。

所有列表、搜索、流式事件、工具注册、检索、原文回取和恢复操作在服务端验证整条归属链。前端过滤只是显示逻辑。Agent 的资源列表由当前 task 的项目身份产生，不能通过模型传入另一个 projectId 扩大权限。

同一物理数据库被多个项目登记时，连接和允许的 schema 仍分别绑定项目；需要真正的数据级隔离时使用独立数据库/schema 和数据库账号。应用项目过滤本身不能改变外部数据库原有访问权限。

Conversation 不只是一组 Task 的分类标签。补充 ConversationMessage 与回合序号，持久化 user/assistant 内容、task 引用、流式完成状态和恢复位置；普通问答使用没有编程执行工具的会话路径，代码任务通过同一会话关联到 Runner。这样不开代码任务也能真正聊天，并在重启后继续。

### 3.2 桌面自动创建流程——必做

1. 用户点击“新对话”，或未选项目直接发送第一条消息。
2. Wails 原生层调用 Windows Known Folder API 获取真实桌面目录，兼容 OneDrive 重定向；不拼接固定的 `C:\Users\...\Desktop`。
3. 在桌面下创建 `ProofCode-Projects`，再原子创建独立子目录，例如：

   ```text
   实际桌面目录\ProofCode-Projects\
     2026-10-08_订单工具_a1b2c3d4\
       .proofcode\workspace.json
       .gitignore
       用户后续创建的源码文件
   ```

4. 本地登记 bootstrapId、machineId、本地目录句柄和非敏感项目身份；以幂等请求创建 Project、Workspace、Conversation。原路径只由本机受信组件持有，控制平面使用 opaque handle。
5. Project 增加 `sourceKind=REMOTE_REPOSITORY|LOCAL_FOLDER|SCRATCH`。远程项目要求仓库 URL；本机与 Scratch 项目允许 URL 为空。对数据库迁移、校验器与 Runner 消息同步修改，不能仅让 UI 不再必填。
6. 普通聊天可以立即保存消息。首次代码任务前，为空工程初始化本地 Git 和最小 `.gitignore`，形成初始提交；编程任务基于实际目录快照建立隔离 attempt 工作树。
7. 持久化目录与项目、workspace、conversation 的映射，重启后恢复。目录重名通过 UUID 后缀和排他创建解决。
8. 磁盘目录创建成功但服务注册失败时，保留 bootstrap 状态供重试；服务注册成功但界面中断时按同一 bootstrapId 回取，不重复建项目。目录创建失败时提示实际原因并提供用户选择其他位置的恢复入口。

`.proofcode` 不保存明文数据库密码、API key 或恢复快照，并从 Git 提交中排除。对话全文与私有恢复对象保存在应用受控存储，工程目录只保存必要的身份映射。

删除/归档对话不会自动删除工程文件或外部数据。移动目录通过显式“重新绑定”更新本机句柄并重新确认源码快照，保留项目身份。

### 3.3 让目录成为实际工作区

当前 Runner 主要通过 HTTP(S) clone 准备仓库。仅创建桌面文件夹仍不足以支持本机写代码，因此增加 `SourceResolver`：

| 类型 | 来源与执行方式 |
| --- | --- |
| REMOTE_REPOSITORY | 延续现有远程 clone + 固定 revision + attempt worktree |
| LOCAL_FOLDER / SCRATCH | 本机 Runner 根据 machineId 与经过登记的句柄取得源码快照，再建立隔离 worktree |
| 远程执行本机来源 | 只接收用户授权的源码快照包，验证 manifest；不能把客户端绝对路径当成服务器路径 |

本机来源快照必须包含用户当前未提交修改和允许的未跟踪文件，否则 Agent 实际编辑的是旧 HEAD。使用私有基线快照/工作树实现，不擅自提交到用户分支；恢复补丁应用到原目录前核验原目录 manifest，发现用户并发修改则要求重新合并。

自动目录可以用于普通问答与代码生成；随后连接的数据库和 Redis 默认都只属于这个自动创建的项目。功能验收必须验证真实文件落到该项目的可审阅产物中，而不只是展示一个路径。

### 3.4 按文件夹展示对话

侧栏显示“项目/目录 → 工作区/分支 → 对话”，列出当前项目的数据连接与恢复记录。切换项目时取消旧请求订阅，清空旧资源详情，再加载新 scope。迟到的 HTTP/WebSocket 响应必须核对 project/workspace/conversation 和请求代次，避免旧项目结果覆盖当前界面。

## 4. 数据库管理：画布与 Agent 共用 Query IR

### 4.1 用户操作与执行闭环

```text
自然语言 / 拖拽查询 / 表格编辑
    → 类型化 Query IR / Mutation IR / Migration IR
    → 校验资源、结构版本、操作范围
    → 编译参数化 SQL、预览差异、EXPLAIN
    → 创建不可变计划
    → 持久化用户批准
    → 消费执行资格并写开始账本
    → 执行、验证、提交或回滚
    → 结果、审计、可用的恢复入口
```

画布拖动不会直接改变数据库。连接表节点与字段产生查询草稿；调整字段顺序只影响显示；新增/删除字段产生结构变更草稿。用户选择“应用”后才进入批准链路。

自然语言与手工操作共享相同 IR 和编译器。LLM 负责提出草稿，确定性校验器负责字段存在、参数类型、条件范围、能力支持与审批契约；校验通过不等于业务意图必然正确，仍需用户预览和测试。

### 4.2 核心后端实体

| 实体 | 核心字段与职责 |
| --- | --- |
| DataResource | project、名称、provider、environment、credentialRef、allowedSchemas、resourceVersion、policyVersion、禁用状态 |
| DataSession | 无编程任务也可使用的管理会话，绑定项目、资源、操作者、权限、有效期 |
| SchemaSnapshot | 表、列、类型、主键、唯一约束、外键、索引、注释、版本哈希 |
| OperationPlan | 来源 task 或 dataSession、规范化 IR、预期影响数量、前置条件、差异、digest、状态 |
| ChangeSnapshot | 行级前/后镜像或缓存状态、对象哈希、私有加密、保留期限 |
| AuditEvent | requestId、scope、actor、plan、批准决定、状态、数量、错误码与来源引用 |

加入 DataSession 很关键：数据库管理和恢复不应依赖一段编程任务一直处于 RUNNING。当前任务终结后不能再创建 Redis 补偿计划的限制将在这里解除；恢复仍创建新计划与新批准，不复活旧执行资格。

### 4.3 查询与编辑分阶段交付

| 第一阶段 | 第二阶段 |
| --- | --- |
| PostgreSQL 连接测试、保存名称、更新/禁用/轮换 | 其他数据库适配器 |
| 结构树、主键/外键/索引信息、结果分页 | 基于显式关联字段的只读 JOIN |
| 类型化 AND/OR/IN/IS NULL、排序、受限计数 | GROUP BY 与白名单聚合表达式 |
| 主键或唯一键定位的行编辑与前镜像 | 有数据恢复策略的受限 Migration |
| 参数预览、EXPLAIN、审计与恢复状态 | 完整关系画布与结构变更对代码的影响分析 |

分页优先使用主键游标，结果限定行数、字节数、查询时间和环境。没有稳定唯一键的表可以查询，但不开放容易覆盖多行的直接表格编辑。

SQL 由结构化表达式树编译。标识符来自当前允许的 schema/表/列，值使用参数绑定。禁用任意 SQL、任意函数、拼接脚本等旁路。EXPLAIN 默认不带 ANALYZE，并使用限制过的连接；带实际执行的分析功能需单独定义授权。

初期维持现有数据 IR 执行的批准要求。后续可提供用户明确开启、有期限和范围的只读浏览授权；该授权不能覆盖写入、DDL、TTL 修改或恢复。

### 4.4 PostgreSQL 写入与自动记录

每次写入：持久化执行意图 → 目标数据库事务 → 锁定或校验目标行及版本 → 收集受限前镜像 → 执行 → 验证 affectedRows 和后置条件 → 提交 → 补记审计。

在锁定目标行的事务中取得前镜像，加密恢复对象及 operationId/hash 绑定必须在目标提交前可靠持久化；持久化失败则回滚目标事务。后镜像/行版本与结果引用也纳入可核对记录。失败事务可能留下孤立快照，需标记未确认并清理，不能把孤立对象当作写入已生效的依据。

用户预览后数据被其他客户端改动时，不能用旧值无条件覆盖。通过行版本、关键字段前像哈希和必要锁定拒绝过期计划。大批量操作对快照大小、耗时和影响范围设限，超限需新的明确方案。

密码留在凭据存储；完整行镜像和缓存值属于私有加密恢复数据。公开审计只放有限元数据、数量、状态、哈希和引用；敏感字段预览需脱敏。用户提交 IR 中的实际参数也属于私有计划内容，不能因此写入公开项目或论文附件。

## 5. 批准前误执行为 0：硬门槛与恢复语义

### 5.1 必须满足的不变量

针对受控数据网关的任何外部变更：

```text
发生变更
  ⇒ 当前上下文有权限
  ∧ 计划所属 project/resource/环境与执行目标一致
  ∧ 用户已持久化批准同一计划摘要
  ∧ resourceVersion/policyVersion/schemaVersion 未变化
  ∧ task attempt 或 DataSession 仍有效
  ∧ 一次性执行资格已原子消费
  ∧ EXECUTION_STARTED 已持久化
```

摘要包括 project/workspace/conversation 或 DataSession 身份、task/attempt、resource/provider/environment、资源和策略版本、schemaVersion、IR 版本、规范化 IR、expectedRows、预条件与有效期。批准后改一项参数或更换连接配置，都必须重新生成并批准计划。

以上上下文、权限、批准与版本在取得执行 claim 时原子核验，并把连接端点、凭据版本和策略快照固定到该次执行；外部 secret 轮换也必须更新被摘要绑定的资源版本，不能在结构检查与 DML 时分别解析到不同目标。执行 claim 之后的取消/撤权只能尝试中止尚未完成的操作，不能承诺撤回已经发送或提交的事务；审计记录其实际结果。

普通“自动执行代码/命令”开关不得放行数据网关。Runner 不持有项目数据库密码；数据库网络/账号权限限制在数据网关。否则模型仍可能通过 shell 或其他网络工具绕开批准，不能把网关断言宣传成整个主机上的无条件保证。

当前逐计划模式下，未获批准的 `data_execute`，包括 SELECT/get/SCAN，都不得调用执行适配器。连接探测、结构读取与无 ANALYZE 的 EXPLAIN 使用已配置的元数据权限并留记录。未来只读浏览会话只有在用户明确授予范围与期限之后才执行读取；该授权不减少写操作的逐计划批准门槛。

“批准并执行”按钮可以组合两个服务端步骤，但批准必须先持久化，执行再核验，不以界面按钮状态作为授权凭据。

### 5.2 四种恢复情况

| 情况 | 正确处理 |
| --- | --- |
| PostgreSQL 事务内失败、验证失败 | 确认 ROLLBACK，记录失败与验证证据 |
| PostgreSQL 已确认提交后要求撤销 | 生成新反向计划，绑定主键、前像与后像/行版本；新事务锁定并确认当前仍匹配原后像和结构前提，批准后恢复；不匹配则冲突 |
| 连接中断，无法确定提交是否发生 | COMMIT_UNKNOWN；先核对，不自动重放，不谎报已回滚 |
| Redis 已写入后需要恢复 | 根据私有快照生成另行批准的条件补偿；不满足条件时返回冲突 |

已确认写入后的“撤销”可能受到外键、触发器、后续数据和数据丢失影响，不能承诺任意时刻完整一键恢复。PostgreSQL 与 Redis 之间也没有全局事务回滚；跨存储操作使用步骤账本和有条件补偿。

### 5.3 审计与提交之间的故障窗口

控制平面数据库与目标数据库不是同一事务。开始账本落盘失败时不执行；目标已提交但结束审计失败时不能把数据说成回滚。若控制平面事务不可用，连 `AUDIT_PENDING` 都可能无法落盘，崩溃后只剩 `EXECUTING`；必须有目标端事务账本或另一个可靠持久化提交凭据，才能在恢复时确认已提交并补记。无法确认的执行保留 outcome unknown，只做核对，禁止再次执行。后台核对依据是已落盘的开始记录、目标端账本和可验证凭据，不依赖进程内队列。

分开保存 `executionOutcome` 与 `auditDeliveryStatus`。只有结果凭据已可靠持久化，才可认定 `COMMITTED + AUDIT_PENDING`；找不到凭据不意味着没执行。

对允许安装执行账本的 PostgreSQL，唯一 operationId/digest、结果/恢复引用与必要提交事件和业务 DML 在同一目标事务提交。断线后可通过该记录核对并恢复结果。在不具备此权限的连接上，无法判断结果就保留 unknown；不靠无限重试获得表面成功。这不能扩展成跨数据库、缓存或外部触发器副作用的 exactly-once 承诺。

### 5.4 强断言验收

以下均使用可销毁 PostgreSQL/Redis，同时检查目标状态、适配器调用、持久批准和审计：

- 未批准、已拒绝、伪造/过期资格、跨项目、旧 attempt、终结上下文、摘要不匹配：外部变更调用为 0，行/键状态未变化。
- 批准一个计划不能执行另一个；更换资源、参数或策略后旧批准失效。
- 并发执行与重复派发只能取得一个执行 claim；恢复时不得重放 unknown 操作。
- 开始账本持久化失败时变更调用为 0。
- PostgreSQL 中途失败、行数不符与验证失败确认回滚；断线故障分别模拟提交前、提交后、确认丢失。
- Redis 补偿必须重新批准；其他客户端改值、TTL 条件不符时拒绝覆盖。
- 切换项目后连接、计划、审计、原文引用、恢复快照均不可跨项目取得。

“批准前误执行次数=0”是发布门槛，覆盖 SQL 写入、DDL、Redis 写/删/TTL、补偿和反向迁移。不能仅用模型自述或某个 HTTP 状态证明它。

## 6. Redis 可视化管理与项目缓存隔离

### 6.1 第一版管理能力

连接列表与测试、名称/环境/状态、游标 SCAN、键类型/TTL/大小、值按需读取、字符串编辑、删除与过期设置、操作历史、加密恢复快照和条件补偿入口。

使用 SCAN 返回游标与有限元数据；SCAN 不是一致性快照，需要去重并允许重复/变化。不通过 KEYS 拉全库，不把所有值塞入模型上下文。TTL 与值视图带读取时间，执行计划重新检查条件。

后续分别扩展 hash/list/set/zset，每种类型定义独立 IR、大小限制、并发校验与补偿规则，不用“执行任意 Redis 命令”代替类型化管理。

### 6.2 命名空间与 Redis Cluster

当前命名空间包含 project 和 environment，但不包含 resourceId；同项目同环境的两个连接若指向同一 Redis 实例，会看到同一前缀。新命名空间加入 resourceId，并计划旧前缀迁移与明确的兼容策略。

当前适配器是 standalone，本阶段先交付 standalone 管理。将来支持 Cluster 时使用拓扑感知客户端、各主节点独立 SCAN 游标以及跨页去重/失效规则，不能仅靠 key hash tag 声称已经支持 Cluster。

新管理命名空间可采用 `pc:projectId:resourceId:environment:{keyTag}:value`，对应版本/执行元数据共享 `{keyTag}`；keyTag 由项目、资源、环境和逻辑键的规范编码哈希产生。这样每个逻辑键及其元数据位于同一 slot，不把整个项目都集中在单个 slot。多业务键的原子修改仍需单独约束，不承诺跨 slot 事务。逻辑键由网关拼接与校验，禁止客户端选择任意前缀；新旧命名空间切换不能悄悄改变已经批准计划的目标。

对于用户已有应用键空间，显式配置允许的前缀与只读/读写权限；不能因为系统新建了隔离前缀，就默认具备整个 Redis 实例的管理权限。

### 6.3 补偿边界

Redis 的 MULTI/EXEC 不提供 SQL 事务式回滚，Lua 脚本也不能把运行时错误自动还原。执行前先做类型、权限、大小与条件预检，失败后的恢复使用独立补偿计划。

在所有写入都经过网关的管理命名空间，单调版本、generation/tombstone 与操作凭据和写入/删除/设置 TTL 原子更新；TTL 的绝对到期时间记录在元数据中，值自然过期后元数据不会一起消失或把历史版本归零。元数据至少保留到对应恢复快照失效；丢失、淘汰或来源不明时拒绝自动恢复，不能把“键不存在”当成恢复许可。部分执行出错或确认丢失也保留未知结果，版本记录没找到不是重写理由。

对外部应用也能直接写入的共享键，仅比较值相同不能检测“修改后又改回”的 ABA 情况。无法证明并发条件与版本连续性时拒绝自动补偿，不覆盖可能的新数据。TTL 过期也不自动解释为可恢复授权。

### 6.4 两类缓存分别管理

| 缓存 | 定位 | 管理内容 |
| --- | --- | --- |
| 用户项目 Redis | 用户应用的数据资源 | 键、类型、值、TTL、批准、恢复 |
| ProofCode 内部索引/结果缓存 | Agent 的性能组件 | 命中率、大小、scope、TTL/版本失效、清理与重建 |

两者都按项目授权，但使用不同凭据、存储与 API，避免把开发者清理 RAG 缓存变成误删业务 Redis。

## 7. 版本感知、证据约束的混合分层 RAG

研究暂名：**版本感知证据路由 RAG**。项目贡献是“先确定可用证据版本，再按结构召回、反馈迭代，并在修改前核验原文”。这是待验证的组合设计；不能在没有文献和实验比较时宣称全球独一无二。

### 7.1 版本身份先于相关性排名

建立不可变 RevisionDescriptor：

```text
projectId + workspaceId + sourceKind
resolvedCommit + indexTree + workingManifest
parserVersion + indexVersion
```

分支名保存为选择来源，但真正定位使用解析后的 commit。workingManifest 含允许的当前文件路径与字节哈希，表示未提交修改、删除和允许的未跟踪文件。staged tree 与当前工作区分别记录，不能把 Git HEAD 等同于用户现在正在编辑的内容。

task/attempt/会话作为证据使用与权限来源；不可变文件块按内容哈希复用，避免把所有解析缓存都重复绑定到每个任务。查询结果仍按实际 scope、revision、权限、过滤条件与配置隔离。

历史内容进入私有内容寻址存储，RevisionManifest 保存路径到块/文件哈希的映射。相同字节可共享物理存储，但证据 ID 仍包含版本和路径。块的 SHA-256 与 Git blob object ID 分开命名。

规则：

- 默认检索当前工作区快照。
- 用户指定 commit 或分支时，先解析到唯一版本；指定某次 task attempt 时还需 step/checkpoint，因为一个 attempt 内会多次修改源码。未指定 step 时，在请求开始冻结到该 attempt 明确的最近已确认检查点，并返回所选 revision/checkpoint ID；无法唯一解析时列出候选或报告缺失，不能改搜最新版。
- 普通结果在融合前硬过滤项目、权限和版本；相似度再高的旧版本也不能充当当前证据。
- 用户明确比较两个版本时，返回两个分别标记的证据集合，不把 v1 行号与 v2 内容拼成一个结果。
- 历史快照按保留策略管理；任务检查点与论文实验版本可 pin，过期或未保留版本明确报告不可回取。

### 7.2 分层检索流程

| 层级 | 机制 | 作用 |
| --- | --- | --- |
| L0 版本/权限路由 | project、workspace、revision、允许的文件/结构范围 | 先排除错误项目、错误版本与无权内容 |
| L1 文件定位 | 路径、标识符、精确报错/字符串、BM25 类倒排检索 | 在仓库内找候选文件 |
| L2 语法片段 | Tree-sitter 的函数、类型、作用域、import | 比固定 80 行块更好地保留代码边界 |
| L3 关联扩展 | 有限 import/调用引用、对应测试、变更邻接、Schema/迁移关系 | 补齐修复需要的关联证据 |
| L4 融合与预算 | 加权 RRF、去重、多样性、覆盖度与 token 成本 | 在预算内组织可追溯上下文 |
| L5 验证反馈 | 当前编译/测试错误、已读/已改对象、新 revision | 下一轮针对失败补证据 |

不把静态语法引用宣传成完整运行时调用图。解析失败时保留路径/词法降级并记录状态；新增的向量召回将来可以作为独立路由接入，本阶段不依赖它，也不讨论模型部署。

RRF 基础可用 `Σ w_i/(60 + rank_i)`；参数只在开发集调整。上下文选择按“相关性 + 新覆盖 + 错误定位 − 重复覆盖”相对证据 token 成本做贪心选择，并限制单文件占用。版本过滤是硬条件，不通过给旧版本扣分来代替。

反馈按 task step 与错误指纹保存。一次对应验证已通过后，旧错误标记 resolved；避免当前实现一直把最近历史失败追加到所有后续查询。限制扩展深度、候选量和迭代次数，记录每次检索实际解决的依赖。

### 7.3 代码与结构证据联动

RAG 索引经授权的 schema、表/列/约束、迁移以及代码中对它们的引用。数据库结构证据绑定 `projectId/resourceId/environment/schemaVersion/resourceVersion`；结构改变使相关关系边和查询结果失效。

不要假定所有工程都使用某一种 ORM。先以显式迁移、实体映射、查询字符串的静态关联建立线索，结果标注关联依据与不确定性。默认不索引数据库业务行、Redis 值、凭据与恢复快照；用户授权取得的数据也保持独立 scope 和保留策略。

### 7.4 原文核验与增量索引

每条证据携带 revision、路径、行/字节范围、内容哈希、路由与源对象引用。应用 patch 前重读目标文件核对预期哈希，在受控工作区写锁或版本化 CAS 契约下检查并写入；patch 后生成新快照并更新改动文件的符号和关系。普通文件哈希检查与后续写入并非跨外部进程的原子操作；用户或其他程序同时修改时保守报告冲突，不能声称阻止所有外部并发写入。

内容变化只重新解析相关文件；删除/重命名更新当前路径映射，历史证据继续指向旧快照。watcher 只提供变化提示，读取证据时仍核验内容；丢事件、重启或版本切换时执行回退扫描。不得通过忽略一致性来宣称热缓存速度。

当前一大缺口是每轮双重扫描。新索引拆分为不可变基础索引和 dirty overlay，并支持持久化倒排/符号索引；二者完成后作为同一不可变 generation 原子发布，查询仅使用该 generation 对应 manifest 的原文对象。命中文件核验不能发现未命中文件或新文件的遗漏变更，因此热查询只描述为“最近已校验快照”；需要当前全仓一致性且无法确认时，先校验/扫描再发布新 generation。不得把临时读到的新内容拼进旧 revision。后台与关键检查点全量核对，正确性无法确定时保守回退。

## 8. 可回取、可审计的上下文压缩

目标是控制输入量并保护关键事实。完整历史始终保存，但较短模型视图仍可能丢失可见信息，不能把“保留原文”误称为模型理解无损。

### 8.1 双层记录

| 层 | 内容与职责 |
| --- | --- |
| 原始 Transcript / ContextObject | 完整消息、原始工具结果、时间顺序、调用 ID、哈希，私有持久化 |
| 模型视图 | 本轮保护内容、检索证据、短引用、来源索引与预算内摘要 |

新增只读 `context_read(referenceId, offset, maxBytes)` 工具及对应授权 API。referenceId 绑定当前项目、会话/任务、源对象和哈希；回取重新核验当前权限，不能通过猜测引用读取别的项目。

压缩替换保持 assistant tool call 与 tool result 成组对应。不会创建孤立工具结果、改写参数或把引用伪装成工具真正输出。

### 8.2 保护与压缩规则

保护系统约束、当前目标、仍有效的早期用户要求、批准与拒绝决定、待执行计划、最近未解决失败、当前版本关键源码与验证证据。

先折叠重复成功日志，保留最新完整副本；过长但可分段读取的历史输出保存对象并用短索引代替。源码与 SQL 不由生成摘要替换成执行依据；关键错误保留完整代表和新差异，第一版继续保守保护错误全文。

建立 ConstraintLedger，每项约束带原用户消息引用、状态和明确的替代来源。LLM 摘要可作为导航，但不能凭空生成授权，不能自行把用户未撤回要求标记失效。

预算不足时优先去重复与已被新结果取代的旧输出，再减少低价值证据；仍不足则明确标记缺失历史并回取。全部强保护项作为整体校验，包括仍有效的早期用户要求、当前请求、待批准计划和未解决失败；总量仍超预算时直接报错或采用可审核的阶段化输入，不能静默丢弃早期要求或其他关键事实。

### 8.3 可观测与恢复

每次准备模型输入记录保护项、折叠项、短引用、丢弃项、原文哈希、估算/实测口径与回取次数。原对象、压缩视图和引用跨暂停/重启保持可校验；对象不可用时回退原 transcript 或明确失败。

预算按配置的上下文容量、输出保留和工具 schema 开销计算，不继续假定所有接口都有相同上下文上限。可用 tokenizer 时测实际模型输入 token；提供方 usage 单独记录。只存在 `bytes/4` 时明确标成估算，不能给出真实计费节省比例。

## 9. 低幻觉与速度的可执行措施

| 措施 | 能保证或改善的部分 | 不能直接推导的结论 |
| --- | --- | --- |
| 版本硬过滤与原文哈希 | 防跨版本引用与修改过期内容 | 不能证明业务理解正确 |
| 类型化 IR、参数化编译、批准摘要 | 控制结构、范围与授权 | 不能证明自然语言意图一定转换正确 |
| 固定 evaluator 与测试 | 独立核验补丁/SQL/恢复结果 | 不能保证未覆盖功能没有问题 |
| 内容寻址、增量解析、倒排索引 | 减少重复解析与候选扫描 | 速度收益需冷/热缓存实验 |
| 分层预算与原文回取 | 降低无关历史输入，保留追溯能力 | 回取增加时可能抵消延迟收益 |
| 操作 claim、持久账本与 unknown 状态 | 避免盲目重放与伪造完成 | 不等于任意外部副作用 exactly once |

内部查询结果键包括项目、workspace、revision、有效权限与资源版本、query、resolvedFeedback、路由/解析器版本、结果预算。失效由内容、schema、权限或策略版本触发；TTL 只是附加清理机制。缓存只复用结果/证据，不能复用执行资格或用户批准。

## 10. 必须完成的六组对照：真正运行并导出结果

六组是必须运行的配置，不能只在论文中列指标。延续已有版本化实验 profile：

| 组 | 工具 | 附加确定性策略 | Jev 路由 | 分层 RAG | 压缩 | 失败反馈 |
| --- | --- | --- | --- | --- | --- | --- |
| A：纯 LLM | 不暴露 | 关 | 关 | 关 | 关 | 关 |
| B：LLM + 确定性策略 | 开 | 开 | 关 | 关 | 关 | 关 |
| C：LLM + Jev | 开 | 关 | 必须有效 | 关 | 关 | 关 |
| D：LLM + RAG | 开 | 关 | 关 | 开 | 关 | 关 |
| E：LLM + RAG + 压缩 | 开 | 关 | 关 | 开 | 开 | 关 |
| F：完整 ProofCode | 开 | 开 | 必须有效 | 开 | 开 | 开 |

所有组保留共同的工作区、路径、命令与数据库批准底线。可关闭的是实验附加模块；不能为获得 A/B 对比而让真实数据库免批准。

A 不调用工具；输出统一 diff 或声明式数据操作建议。独立 evaluator 审查并应用产物，再运行与其他组相同的验收。对于代码任务，固定实验输入可以包含一份为全部组共同提供、版本化的初始文件包，不由标签答案挑选“正确文件”，也不称为 A 使用了自适应 RAG。

本轮不研究或部署模型。正式实验固定现有生成接口的模型版本与参数；C/F 沿用 Jev 适配器。路由服务缺失、低置信度或错误时 C/F 必须明确失败，不能悄悄退化成 B/E 或从报告删掉。

### 10.1 一次实验如何真正完成

1. 建立版本化任务集：任务描述、完整 baseCommit、允许环境、统一初始输入、独立验收、涉及的正确文件/版本/行区间标签。
2. `POST /api/experiments` 创建同任务的 A–F 独立 runs，冻结 prompt、接口版本、temperature、预算和重复次数；实验 manifest 还固定 Agent 引擎 commit/build、检索/压缩算法版本、索引配置、profileVersion 与 token 计数口径。被修改工程的 baseCommit 不能代替引擎版本。当前 v1 四路启发式与新分层实现分别标识，升级配置时生成新版本，禁止混为同一 D/E 历史结果。
3. 每个 run 使用新 worktree；数据库/缓存任务使用可销毁的独立实例或 schema/命名空间，重置数据和版本，禁止组间共享变更。
4. evaluator 保存独立测试，不允许 Agent 修改它来获得通过。源码标签和判分答案不进入 Agent 上下文。
5. 记录真实工具执行、批准、检索引用、压缩视图、补丁、测试输出和逐 run 证据；配置失败、超时、取消、unknown 均保留。
6. 输出固定格式 JSON/CSV、实验 manifest、证据哈希与图表，重复运行后检验源输入和 profile 是否相同。

冷缓存和热缓存分别运行；随机或平衡组顺序，分开记录人工批准等待与自动执行时间。失败不无限重试；重试策略预先固定。提供方未给 token/显存等测量时记录缺失，不用 0 代替。

### 10.2 任务集与样本规模

先做覆盖六类场景的 6 个联调任务，每组重复 3 次，即 108 个计划 run；这只是建议规模，没有声称已经运行。正式任务集建议扩充至约 30 个任务，再按可用预算固定重复次数。

六类场景：局部 bug 修复、跨文件接口改动、测试失败驱动修复、同文件多版本/分支定位、长对话与恢复、数据库/Redis 联动。各组使用同类任务与统一验收，避免只给 F 简单任务。

代码能力和数据库能力分开汇总。A–E 没有 F 的数据工具时可生成 IR，再由相同的受控 evaluator 检查，写入仍必须获得实验操作者的明确批准。纯规划正确率与完整执行成功率标明差别，不能直接混为同一指标。

### 10.3 解释结果需要的补充对照

A 到 B 同时增加工具和附加策略，不能把差异全部归因于策略；C 到 B 也改变了策略。因此在六组之外增加一个共享工具但无附加模块的 T 组，或等价的受控小实验。

RAG 专项比较：现有四路 RRF → 加语法分块 → 加关系扩展 → 加版本路由 → 加失败反馈。压缩专项比较：不压缩 → 当前日志去重 → 可回取分层压缩。F 的子项关闭实验可用于归因，但不能冒充原固定 A–F profile；新配置采用单独 profileVersion。

### 10.4 指标用于支持对照，不替代对照

Agent：工具错误/无效调用、任务与测试结果、危险操作拦截、实际输入/输出 token、自动执行与总时延、p95、恢复。显存仅在实际可测时记录，本阶段没有模型部署不保证该值可得。

RAG：Recall@K、MRR、NDCG、文件/行与 revision 命中、有效哈希、过期引用、patch/test、冷热缓存延迟、token 变化与压缩后的错误。

数据库：自然语言到 IR 的标签正确性、IR 编译与真实执行、EXPLAIN、危险操作/误报、事务回滚/提交后恢复/Migration 恢复分别统计、审计、批准前误执行。

版本选择的验收额外覆盖同文件多个 commit、staged/dirty 内容、分支同名文件、删除/重命名、不同 task/attempt、schema 漂移。至少报告样本数、失败与缺失原因；少量样本不作广泛性能结论。

## 11. 用户数据库 Migration 与代码联动

ProofCode 自身的 Flyway 迁移不算用户数据库 Migration。用户迁移使用独立 `MigrationIR`，包含基础 schemaVersion、有限 DDL 步骤、预条件、验证、可逆性、备份/前像引用和恢复策略。

初期仅 PostgreSQL 的受限、可事务执行 DDL：建表、加可空列、普通索引等。在临时数据库重建基础结构，验证迁移、约束和恢复，再展示 schema diff 与相关代码补丁。`CREATE INDEX CONCURRENTLY` 等不适用同一事务的动作采用专门流程，不塞入通用原子迁移。

删列和有损类型变更的反向 DDL不能恢复丢失的数据；必须区分结构恢复与数据恢复。初期可拒绝高风险自动执行，保留经审阅的草稿。

代码、数据库、Redis 联动采用有步骤的变更包：代码补丁 → 临时数据库验证 → 独立批准 → 向后兼容数据库变更 → 代码应用 → 必要且另有批准的缓存失效 → 验证。每步有依赖与结果账本；后续失败不能自动声称前面已提交的所有存储都回滚。

## 12. 交付阶段与分支管理

| 阶段 | 具体交付 | 通过门槛 |
| --- | --- | --- |
| P1：项目入口 | sourceKind、desktop bootstrap、本机 SourceResolver、目录会话树最小接入 | 不导入目录可对话；真实桌面目录、重启/重试不重复；代码来源含 dirty 内容 |
| P2：数据管理闭环 | DataSession、资源名称与生命周期、版本摘要、查询分页/行编辑、Redis 管理与终态后恢复 | 跨项目全链路拒绝；批准前变更为 0；真实失败回滚与补偿冲突可复现 |
| P3：证据与压缩 | 历史 manifest、语法分块/关联、版本路由、context_read、约束台账与增量缓存 | 同文件历史/当前明确区分；过期 patch 拒绝；原文可回取、协议完整 |
| P4：可视化与迁移 | DB 结构/查询画布、表格差异、缓存管理页面、受限 Migration 与代码关联 | 拖动只改草稿；页端操作都经统一 IR/批准；临时库迁移与恢复有证据 |
| P5：正式比较 | A–F 与专项消融、真实输入与独立验收、证据包与图表 | 六组完整展示；真实 run 可复现；缺失不伪造；批准前误执行为 0 |

实验框架从 P1 开始维护，每个阶段补相应任务；P5 是正式完整比较，不是到最后才建立实验开关。

建议分支：`codex/project-workspace-bootstrap`、`codex/data-sessions-and-recovery`、`codex/versioned-evidence-rag`、`codex/retrievable-context`、`codex/data-workbench`、`codex/thesis-controlled-comparisons`。每阶段独立可审阅提交，记录 baseCommit 与实验 profile 版本，推送远程并保留 Git bundle/必要私有快照。数据凭据、恢复对象、用户数据库内容和未脱敏历史不进入公开仓库。

现有主工作区未提交修改保持原状；本方案在独立 `codex/` 分支提交。工程与论文结果以实际代码和证据更新，计划不计为已经实现。
